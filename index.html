The open way in

The gates on the web today trust platforms. A bot filter lets an agent through when its vendor is in the filter's directory. A large service lets an assistant in after a partner deal. The assistant that your customer runs on their own computer has neither, so it gets a CAPTCHA.

Kiosk asks for two things that any assistant can produce: a key that it made for your site, and a proof of work that it paid for in compute. Let's Encrypt gave every website a certificate without asking who runs it. Kiosk gives every assistant a way in on the same terms, and puts a price on abuse.

How it works

  1. Find. Your site serves the standard discovery files: agents.txt, auth.md, an API catalog (RFC 9727) and /.well-known/kiosk.json. Where humans link accounts, it also serves OAuth server metadata (RFC 8414).
  2. Register. The assistant makes a new key for your site and proves that it holds it. Its access tokens are bound to that key (DPoP, RFC 9449). There is no email and no password. Another site gets a different key, so the key gives two operators nothing to connect.
  3. Pay the toll. Registration and each new session cost a memory-hard proof of work: about 10 seconds on one laptop core. Your server checks it in about 20 ms. The more a customer spent with you in the past week, the fewer sessions pay, down to none at 100 euros.
  4. Call. Each query and action that you declare is its own REST endpoint, listed in a public catalog. One skill file teaches an assistant to use every Kiosk operator.
  5. Pay. You sign a checkout with the exact items and price. The assistant pays it with two signed AP2 v0.2 mandates, and you answer with two signed receipts. The human saves a card once, on your own Stripe page. After that, every payment at your service needs no form and no click.

For operators

  • Your customers' AI assistants come to you directly instead of scraping you. You keep the customer relationship and the data.
  • Add a Ruby gem, an initializer, the migrations, and one controller with your own queries and actions. Read the guide.
  • A human links their assistants to their account. Each assistant has its own spending cap, and the human can revoke it alone.
  • Gate an action on anonymized attributes such as “18+” or a licence category.
  • Payments go through your own Stripe account. Kiosk takes no cut.

For AI assistants

Read the skill. An assistant needs:

  • Filesystem — store an RSA keypair per origin at ~/.kiosk/<origin>/
  • HTTP — REST with JSON + JWS signatures
  • Crypto — sign AP2 v0.2 mandates (two SD-JWTs) with RS256
  • Code — Python for JWT signing, Equihash PoW solving and the event listener

What ships

  • The specification, with a formal version and JSON Schemas for a port to another stack.
  • The skill that an assistant reads, versioned and pinned by its SHA-256.
  • The reference implementation: a Rails engine, the proof of work, the Stripe payment adapter, the KYC check and an attack test suite, as Ruby gems.
  • The seven demo operators above, with their source.

Built on open standards:

  • agents.txt
  • auth.md
  • Agent Skills
  • RFC 8414
  • RFC 9727
  • DPoP (RFC 9449)
  • RFC 9457 problems
  • AP2 v0.2

The reference is Rails. On the wire it is HTTPS, JSON and JWS, so you can port it to any stack.

Status: v0.5 — pre-1.0: the wire may still change between releases, and an assistant relies on the skill file that the operator pins. A known TODO is in the specification: refunds or cancellations that an assistant asks for. kiosk.tech is static files: no request, order or payment goes through it.
Kiosk is an open protocol with an Apache 2.0 reference implementation. No intermediary, no transaction fees.
